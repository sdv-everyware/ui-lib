The UI of the next embedded device

Designed in Figma. Driven by Rust. On Android's core, without its weight. The same button on a home panel, a kitchen appliance, a robot. And an agent builds the next screen alone.

For a program

Give an agent the task and these files; it does not need this site. Each file is small, generated from the sources, and checked before every commit.

Principles

1One truth, one direction

Action → state → UI model → pixels. Nothing on the screen writes back: a tap is an action like a message from a bundle, so a frame is a function of the state, testable on the host.

2Figma decides how it looks, code decides what happens

Geometry, colours, variants and names come from the .fig; which variant shows, what a tap does and the data come from Rust. Figma's Play prototype is for people looking at the design: harry never reads it.

3Names are the contract

A #name on a Figma layer is a field in ui_model.rs. Rename both or neither: everyware_ui_test fails when they drift apart.

4Components are state machines, owned by the library

Pressed, value, focus, variant and transition live in everyware_ui_core. The app routes a gesture by name and acts on the event, so a button behaves the same in every EveryWare app.

5A component on a screen is a slot

A named frame with a preview instance inside; harry clones the chosen variant into it. One component, many places, each with its own texts and values.

6Variants for rare changes, parts for smooth ones

A variant change rebuilds the node (~50 ms on the RB3): kind, disabled, selected. Pressed, fades, thumbs and carets are opacities and meters, display-only, every frame.

7One spec, two readers

components.json names the sets, their variants and transitions. The Figma generator and the Rust library read the same file, so they cannot disagree.

8Roles, not contexts

A component is named by its role (button, list item, tile: Material 3), never by what the app puts in it. A new need extends a property or a part before a new component is made.

One tap, six stages

The architecture of every harry app: the strip on the right of each component page is this pipeline. A tap runs through it by itself.

Designthe Figma file
gestureui_event_listener.rs
HomeAction::Gesture(node, gesture)
The slot frame is named in Figma (#entryway/light). harry hit-tests the drawn tree under the finger and reports Down, Move, Up with that name; the app's listener (written once) turns it into an action of the app. Data from the bundles arrives as actions the same way.
↓
The appfour Rust files
actionsactions.rs
state.light.on(gesture) → Some(ToggleEvent::Toggled(on))
One apply() takes every action. For a gesture it matches the node name and hands the gesture to the component living there; the component updates itself (pressed, on or off) and returns an event when something completed. On the event the app acts: sends the command, opens the sheet.
↓
statestate.rs
pub light: Toggle,
One struct owns everything the screen knows: one component value per place on the screen, and the data. Nothing else remembers anything; a test builds a State, applies actions and reads it.
↓
presenterpresenter.rs
model.light = slot("#entryway/light", &state.light);
After every action a pure function turns the state into the UI model: each component into its slot, with the variant string the component chose, its texts, the values of its parts and the transition of the last change (components.json).
↓
UI modelui_model.rs
light: Slot = "#entryway/light" ["SlotCustomizer"];
One field per #name the app touches. The names are the contract with the design: rename both or neither. The SlotCustomizer turns the field into harry's customizations: which variant to clone, which text, which opacity, which meter.
↓
harrythe framework
harry drawsthe framework, the .dcf
clone the variant → apply the parts → animate → render
harry clones the chosen variant from the Library into the slot, applies the parts, animates by the transition and renders with Impeller. The picture is Figma's (fetched into the .dcf), the decision is the code's. Figma's Play prototype is for people looking at the design: harry never reads it.

The Figma file holds the first and the last stage: the names, the variants, the pictures. The app holds the four files between: one match arm, one field, one slot line per component on the screen, whoever writes them, a person or an AI.

In depth: what lives where (Figma, the code, the spec), compared with DesignCompose

Every component lives in three places that agree, and one file is the source for two of them:

components.json  ──► Figma: the library's component sets, their variants and transitions
                 ──► Rust:  transitions (core/src/transitions.rs)
core/src/<component>.rs   the state machine: gestures in, variant and values out, events to the app
harry/src/slot.rs         the binding: a slot on the screen gets a clone of the variant, with the parts the code sets

On a screen a component sits in a slot: a frame named for the app (#wifi/connect) with a preview instance of the component inside. harry clones the chosen variant into the slot and gives the clone its own values (texts, opacities, meters), so one component can be on the screen many times. The app keeps one Slot field per place on the screen and writes it in its presenter: model.connect = slot("#wifi/connect", &state.connect).

Components are named by their role (Material 3: button, list item, segmented button, tabs, tile), never by what the app puts in them. A new need extends a component by a property or a part before a new component is made.

What lives where: Figma, the code, the spec

Three sources make every frame, and each decides one thing: the code decides what is shown, the spec how it moves there, Figma what it looks like.

WhatWhere it is decidedWho reads it
layout and geometry (where a tile is, a sheet's 880 x 1000)Figma, fetched into the .dcfharry draws it as it is
colours, fonts, radii, shadowsFigmaharry
the variants: every state as a picture (button default / pressed / disabled, toggle on / off, sheet closed / open)Figma, the component sets of the Libraryharry shows the variant the code picks
the #names: which layer the code touchesFigmathe app's ui_model.rs (the contract)
preview texts and picturesFigmaharry, until the code writes its own
which variant is shown nowthe code: State → presenter
what a tap doesthe code: HomeAction::Gesture → the reducer
how long a change takes, on which curvecomponents.json → core/src/transitions.rsthe component's transition()
the data: news, weather, devices, Wi-Fithe code: the bundles → the reducer
the prototype: taps and transitions in PlayFigmadesigners only: harry never reads it

The prototype is for designers. harry has no interpreter for Figma's prototype: the .dcf format has a field for it (View.reactions, from DesignCompose), but the fetcher fills it only from the DesignCompose plugin's synced data (vsw-reactions), the design's file carries none, and the harry framework does not read it. So behaviour is written twice: in the app for the device, in the Figma prototype for Play. When the two differ, the device is right; the prototype is a picture of the code. Known gap: Play opens a sheet in 300 ms ease-out, the device in 550 ms spring (components.json, open).

Compared with DesignCompose. DesignCompose's runtime executes the reactions: a tap that opens an overlay in Play opens it in the app, and the designer owns the navigation. harry keeps the state in one place, the code (one reducer for taps and data alike, deterministic, testable), and Figma supplies the pictures and the names.

Actions

#button

A tappable text button, Material 3's filled, tonal and text button, in two widths.

#icon-button

A tappable button with one glyph and no label, Material 3's icon button, in two sizes.

#segmented

One choice of two to four, Material 3's segmented button: the segments are tap targets, the selected one is lit by opacity.

#tabs

The screen's navigation, Material 3's tabs: the chosen tab is lit by opacity, a tap switches the screen with the screens' effect.

Inputs

#toggle

An on/off switch, Material 3's switch: the value moves the thumb and fades the track, the variant is only the state.

#radio

A group of radio buttons where one option is on; the group owns the selection, each button is a variant.

#slider

A horizontal slider: the fill and the thumb are meters the code moves, the variant is only the state.

#dropdown

A closed pill that opens a list of items below it; the open list and the selected item are opacities, the variant only the state.

#input-field

A one-line text field: the focus ring, the caret and the placeholder are opacities, the variant is only the state.

#keyboard

The on-screen keyboard: rows of keys with a character each, pressed keys fade a layer; one component, not a set.

#keyboard-dock

The screen's one keyboard: an overlay at the bottom with the keyboard component in its slot, open while a field has the focus.

Lists and cards

#list-item

One row of a list, Material 3's list item, with a leading icon or image, a headline, supporting text and a trailing end; rows live in a ListView.

#scrollbar

The thumb of a scrolling list: a vertical progress marker along a track, faded in while the list moves.

#tile

A device's card, Material 3's card for a smart home device: a symbol, a title, a subtitle, a value and the device's control; a tap on the card opens the device, the control inside changes it.

Over the screen

#sheet

The container for anything over the screen, Material 3's dialog and side sheet, with the app's content component in its slot.

overlay (code)

The state machine of anything shown over the screen: closed or open, with the open and close transitions; the base of Sheet and Form.

form (code)

A sheet with input fields: a tap focuses a field, the screen's keyboard dock opens and types into it, Enter submits.

Display

#icon

A 24 px glyph (Lucide) for the slots of other components; display only, no state.

#symbol

The tile of a room's or a device's symbol: 48 px, the soft accent background, one glyph in ink; display only.

#bar-chart

A row of 24 bars, each with a level and an accent; display only. The app decides what a bar stands for.
